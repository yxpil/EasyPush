## ADR-001：Electron 主进程承载全部本地服务

**状态**：已接受

**背景**：接收端需要同时提供 HTTP、HTTPS、WebSocket、WebRTC 信令、DLNA/SSDP 与桌面界面，且必须零账号、零公网依赖地安装在 Windows 上。若拆成独立服务进程，用户需要管理两个进程、两个防火墙入口和两套日志。

**决策**：由 Electron 主进程内嵌 Node HTTP/HTTPS 服务、WebSocket 服务与 DLNA 服务，渲染进程只通过回环地址加载 `/desktop/`；主进程持有证书、密钥、设备状态与所有业务状态机。

**后果**：

- 安装包较大（1.0.0 约 115 MB），但用户只需安装一个程序。
- Chromium 安全更新跟随 Electron 版本，需要主动升级依赖。
- 主进程崩溃会同时终止接收端与 DLNA；单实例锁避免多进程争用端口与状态文件。
- 渲染进程被限制为纯展示/解码，业务逻辑可单测，安全边界清晰。

**备选**：Node 后台服务 + 系统托盘壳（部署复杂）、Go/Rust 原生接收端 + WebView（开发成本与 WebRTC 解码能力不匹配）。

## ADR-002：发送端采用零安装网页，而非原生 App

**状态**：已接受

**背景**：访客设备型号复杂、不能要求安装 App或登录账号；"临时投一下"是核心场景。手机整屏镜像受浏览器安全模型限制，无论是否原生都无法通过网页实现。

**决策**：发送端为纯网页（手机端使用原生 TypeScript + Vite，无前端框架），通过 HTTPS 获取摄像头/麦克风，通过 WebRTC 发送实时画面，通过 HTTP 上传文件。不提供 iOS/Android 原生发送端。

**后果**：

- 访客扫码即用；无需应用商店、账号或后台权限。
- 仅支持摄像头、文件、桌面浏览器屏幕共享与 DLNA，不支持手机整屏镜像。
- 浏览器差异（尤其 iOS Safari）成为兼容性工作的主要来源。
- 网页与桌面端共享 `src/shared` 协议类型，但 UI 分别构建。

**备选**：原生 App（违背零安装目标）、手机系统投屏协议（依赖厂商，不可控）。

## ADR-003：WebRTC 仅使用 host candidate，不配置 STUN/TURN

**状态**：已接受

**背景**：产品承诺媒体与信令不出局域网、无公网依赖、无账号。跨 NAT 场景不在目标内。

**决策**：不配置 `iceServers`，不部署 STUN/TURN，不使用中继；仅依靠局域网内主机候选完成连接。信令经本地 WebSocket 交换，SDP/ICE 不经过第三方。

**后果**：

- 同一子网可用；AP 客户端隔离、跨 VLAN、部分企业网络会导致连接失败。
- 无公网投屏能力；无中继意味着弱网下没有兜底路径。
- 连接建立快、隐私边界清晰、无第三方配额与费用。
- 断线恢复仅在 8 秒宽限内、同一网络路径下有效。

**备选**：公共 STUN（引入公网依赖与 IP 泄露）、自建 TURN（运维与带宽成本，且违背局域网承诺）。

## ADR-004：自建本地 CA 而非公网证书

**状态**：已接受

**背景**：浏览器只在安全上下文（HTTPS 或 localhost）中允许 `getUserMedia` 与 `getDisplayMedia`。接收端使用私有 IP、无公网域名，无法申请受信任的公网证书；要求访客手动忽略证书警告既不可靠，也会训练用户接受中间人攻击。

**决策**：首次启动生成 RSA-2048/SHA-256 本地根 CA（3650 天）与按当前 IP/主机名签发的叶证书（365 天，到期前 30 天或 SAN 变化时重签）。通过 `http://<ip>:<port>/ca.crt` 提供 CA 下载，由用户在各发送设备上手动安装并信任。CA 私钥优先使用 Electron `safeStorage` 加密落盘，不可用时回退为明文 base64。HTTPS 响应使用 `Strict-Transport-Security: max-age=0`，不启用长期 HSTS，以便 IP/端口变化后可立即回退。

**后果**：

- 每台手机/电脑都需一次性安装并信任 CA；iOS 还需开启"证书信任设置"。
- 信任该 CA 的设备理论上可被该 CA 签发的任意证书拦截；CA 私钥泄露的影响范围是整个设备，而非单个站点。产品明确建议不需要摄像头时不要安装，并在停用后删除。
- IP 变化会触发叶证书重签，旧二维码/旧页面可能失效；HSTS 不强制，避免用户被锁死。
- `safeStorage` 不可用时私钥为明文，属于已知残余风险，发布说明必须披露。
- 无需公网、无 ACME、无域名，离线可完成部署。

**备选**：公网证书（私有 IP 不可行）、纯 HTTP（摄像头被浏览器禁用）、`mkcert` 等外部工具（增加安装步骤且仍需手动信任）。

## ADR-005：ticket + 6 位配对码 + 桌面人工审批

**状态**：已接受

**背景**：扫码需要携带一次性上下文；手工输入需要短、可读、可口头传达的凭据；同时必须让电脑端的人对"谁接入了"拥有最终决定权。

**决策**：二维码携带 120 秒有效、一次性轮换的 ticket；桌面同时展示 5 分钟有效的 6 位配对码；两者都只用于**发起**配对请求，最终由桌面审批。审批可"仅本次"或"允许并记住"。错误尝试按 IP 与全局双重限速。

**后果**：

- 访客体验短；配对码本身不是长期凭据，泄露窗口有限。
- 审批是默认安全边界；开启"自动批准"会跳过审批（见 ADR-014）。
- 配对码错误使用统一文案，避免泄露正确码；限速可被分布式来源绕过，属于已知限制。
- ticket 使用一次即轮换，旧截图无法重复使用。

**备选**：仅二维码（不便口头传达）、仅 PIN（易被肩窥/暴力尝试）、OAuth/账号（违背零账号目标）。

## ADR-006：HTTP 与 HTTPS 双栈并存

**状态**：已接受

**背景**：文件上传不需要安全上下文，但摄像头/屏幕共享需要 HTTPS；要求所有访客先装 CA 才能传照片会显著提高门槛。另一方面，完全放弃 HTTP 会让没有 CA 的设备连配对都无法完成。

**决策**：同时监听 HTTP 与 HTTPS，各自展示二维码。HTTP 支持配对、上传、DLNA 与桌面页（仅回环）；HTTPS 额外支持摄像头/屏幕共享。HTTP 页面显著提示"当前为 HTTP 连接，摄像头不可用"并引导安装 CA。

**后果**：

- 访客可先以 HTTP 完成低风险上传，再决定是否安装 CA。
- HTTP 流量在同网段明文可见（包括配对码、会话 Cookie、上传内容），这是明确的残余风险；产品不宣称 HTTP 模式保密。
- 两个端口都需要防火墙放行；端口顺延需同步更新二维码与规则。
- HSTS 使用 `max-age=0`，避免 HTTPS 页面把用户锁在失效地址上（见 ADR-004）。

**备选**：仅 HTTPS（门槛高）、仅 HTTP（无法摄像头）、自动跳转 HTTPS（会让未装 CA 的用户直接看到证书错误）。

## ADR-007：同一时刻只允许一个直播，接管需确认

**状态**：已接受

**背景**：接收端只有一块主屏和一套音频输出；多个并发直播会导致资源争用、声音叠加与审批疲劳。

**决策**：全局最多一个活跃直播与一个待审批请求。新请求在已有直播时进入"接管"流程，桌面显示原设备信息并要求确认；开启自动批准时，**接管仍需人工确认**。新请求若来自当前发送端，可直接替换自己的会话。

**后果**：

- 行为可预测，音频不会混流；资源上限明确。
- 并发场景下后来者可能被拒绝或等待，需要产品文案解释。
- 服务端状态机与前端重连逻辑必须处理 `awaiting-takeover`、`replaced` 等状态。

**备选**：多路直播（UI、音频、带宽复杂度高）、排队（实时性差）。

## ADR-008：桌面 React，手机原生 TypeScript，共享协议层

**状态**：已接受

**背景**：桌面界面状态复杂（直播、媒体、队列、审批、设置、设备、历史），适合组件化；手机页面以短流程为主，追求首屏体积与低端机性能，不需要框架运行时。

**决策**：桌面使用 React 19 + Vite；手机使用原生 DOM + TypeScript + Vite；两端共享 `src/shared` 的类型、协议解析与常量。样式各自维护，但共享设计令牌语义（见 [设计系统](design-system.md)）。

**后果**：

- 手机包更小、无 hydration/框架开销；桌面获得可维护的组件与状态管理。
- UI 组件无法直接复用，需在两端分别实现并保持行为一致；E2E 同时覆盖两端。
- 协议变更必须同时更新共享类型与两端调用点，TypeScript strict 与四套 typecheck 提供保障。

**备选**：统一 React（手机体积/性能浪费）、统一原生（桌面上限低）。

## ADR-009：文件持久化而非数据库

**状态**：已接受

**背景**：单用户、单实例、数据量小（设备 ≤500、历史 ≤200、设置少量字段），没有查询与并发写入需求。

**决策**：使用 `state.json` 保存设置、设备、会话密钥与历史；写入采用临时文件 + `rename` 的原子替换，延迟 120ms 合并写入；读取失败时将损坏文件重命名为 `.corrupt-<timestamp>` 并以空状态启动。上传媒体直接落盘 `uploads/`。

**后果**：

- 无数据库依赖、易于备份与人工检查。
- 全量重写状态文件，数据量增大时写放大；当前上限内可接受。
- 损坏时可能丢失设备/历史（不会阻止启动），需要用户重新配对。
- 单实例锁是正确性的前提；不支持多进程共享数据目录。

**备选**：SQLite（引入原生依赖与迁移复杂度）、IndexedDB（主进程不可用）。

## ADR-010：桌面页与媒体仅限回环访问

**状态**：已接受

**背景**：桌面界面包含设备列表、审批与设置；上传媒体属于用户私有内容。局域网内的其他设备只应访问手机网页与必要 API，不应看到接收端控制面或播放他人媒体。

**决策**：`/desktop/*` 与 `/media/*` 在 HTTP 层校验来源地址必须为回环（127.0.0.0/8 或 ::1），否则返回 403；桌面窗口加载 `http://127.0.0.1:<port>/desktop/`。手机网页、配对、上传与 `/ca.crt` 对局域网开放。

**后果**：

- 即使防火墙误开放，局域网设备也无法读取桌面控制面或媒体文件。
- 桌面窗口不能通过局域网 IP 打开；调试必须在本机进行。
- DLNA 播放使用独立的本机媒体 URL，不经过 `/media/*` 的局域网暴露。
- 依赖回环判断而非认证；若本机存在恶意进程，仍可访问（本机信任边界）。

**备选**：统一鉴权（复杂且无法防本机）、仅靠防火墙（单点失效）。

## ADR-011：内置 DLNA MediaRenderer，而非依赖外部软件

**状态**：已接受

**背景**：电视/音箱生态中大量第三方 App 支持 DLNA，但不支持浏览器投屏；用户期望"现有 App 里能看到 EasyPush"。

**决策**：在主进程内实现最小可用 MediaRenderer：SSDP 响应、设备描述、三个 SCPD、SOAP AVTransport/RenderingControl/ConnectionManager、GENA 事件订阅。控制端点只接受私网/回环来源；回调地址必须与订阅者 IP 一致；直播期间返回忙碌；可被设置关闭。

**后果**：

- 覆盖不支持浏览器的 DLNA 生态，无需额外安装。
- 受第三方控制器实现与编码支持限制；Electron 不能解码的格式会失败。
- DLNA 本身无认证，同网段任何控制器都可推送；通过私网限制与"直播互斥"降低影响。
- 需要 UDP 1900 与组播可达，企业网络可能阻断。

**备选**：集成 Kodi/ReadyMedia（增加依赖与运维）、仅浏览器（放弃 DLNA 场景）。

## ADR-012：无遥测、无外部网络请求

**状态**：已接受

**背景**：会议室与家庭场景对隐私敏感；产品定位是"数据不出局域网"。

**决策**：不集成分析、崩溃上报、广告或云端配置；运行时只监听本地端口。依赖在构建时锁定，运行时不下载字体、图标或脚本。日志仅写本地，按键名脱敏。

**后果**：

- 可离线部署，网络抓包中应只有局域网流量。
- 无法获得真实用户崩溃率与使用数据，问题发现依赖用户反馈与本地诊断。
- 依赖安全更新需主动升级与重新发布。
- 手动检查（抓包、日志抽查）成为验证的一部分。

**备选**：匿名遥测（违背承诺）、仅崩溃上报（仍产生外发请求）。

## ADR-013：2 GB 单文件上限、7 天上传保留、分项限速

**状态**：已接受

**背景**：需要覆盖手机长视频，同时避免磁盘被占满、内存被大文件拖垮；局域网设备可能被恶意或误用刷上传。

**决策**：单文件最大 2 GB，流式写盘，空文件 400、不支持类型 415；单设备 5 分钟最多 30 次上传；上传文件 7 天后清理（应用启动时执行）；历史上限 200、设备上限 500；日志保留 14 天。

**后果**：

- 覆盖绝大多数手机视频；超大文件需用户自行压缩。
- 长期运行不重启时，过期上传不会中途清理；磁盘占用需人工关注。
- 限速是粗粒度保护，不构成 DoS 防御；未做磁盘配额与并发上传总数限制。
- 设备/历史上限防止状态文件无限增长。

**备选**：无上限（磁盘风险）、按天配额（实现与 UI 复杂）。

## ADR-014：自动批准跳过直播审批

**状态**：已接受（高风险，默认关闭）

**背景**：演示/自助场景中，操作者可能希望访客无需等待电脑端确认；但直播会直接占用大屏与音频，属于高风险动作。

**决策**：提供单一 `autoApprove` 开关，开启后同时跳过配对审批与直播审批；**接管仍必须人工确认**。设置页展示明确警告；安全文档与发布说明披露该权衡。默认关闭。

**后果**：

- 开启后，任何能访问端口的局域网设备都可直接配对并发起直播，无需电脑端在场。
- 与"所有高风险动作默认需要审批"的产品原则冲突，因此作为显式、可审计的例外存在。
- 不改变鉴权、Origin/Host 校验、直播互斥与停止能力；电脑端仍可随时停止。
- 建议仅在隔离的演示网络短期使用，用后立即关闭。

**备选**：仅跳过配对审批（仍无法自助直播）、仅对"已记住设备"自动批准（实现更复杂，风险仍存在）。

## ADR-015：仅发布 Windows x64，且暂不签名

**状态**：已接受（临时）

**背景**：目标用户以 Windows 会议室/家庭电脑为主；代码尽量跨平台，但 1.0.0 的验证资源集中在 Windows。代码签名需要证书采购与组织身份，当前不具备。

**决策**：electron-builder 仅配置 Windows x64 NSIS，按用户安装；不提供 macOS/Linux 安装包；安装包暂不签名，发布时提供 SHA-256，由用户/管理员核验。

**后果**：

- SmartScreen 可能拦截，降低首次安装成功率；企业分发需额外审批。
- 无自动更新，安全修复依赖手动升级。
- macOS/Linux 可运行源码但未验证、未打包，不在支持范围。
- 后续获得证书后可补充签名，不改变应用架构。

**备选**：等待签名后再发布（阻塞交付）、提供未测试的跨平台包（扩大支持面）。

## ADR-016：URL 媒体使用原生播放器 + hls.js，不做服务端转码

**状态**：已接受

**背景**：桌面端需要播放手机粘贴的媒体直链，包括 HLS；接收端不应成为转码服务器（CPU、延迟、版权与复杂度）。

**决策**：图片/音频/视频直链交给 Chromium 原生播放器；`.m3u8` 在支持时使用 hls.js，失败时回退原生 HLS（如 Safari 发送端不涉及）。不代理、不转码、不下载到本地（上传文件除外）。仅接受 http/https 直链，拒绝本地文件与危险 scheme。

**后果**：

- 支持常见 MP4/WebM/MP3/JPEG 与 HLS；MKV/AVI/HEVC 是否可播取决于 Chromium。
- 跨域 HLS 需要对方提供 CORS；DRM、需要登录或防盗链的 URL 会失败。
- 无转码意味着低端设备解码压力由接收端承担。
- 不存储 URL 内容，重启后需重新添加。

**备选**：服务端 ffmpeg 转码（依赖重、CPU 高、法律风险）、仅本地上传（失去 URL 场景）。

## ADR-017：日志采用本地 JSONL，按天轮转

**状态**：已接受

**背景**：故障排查需要结构化、可附加字段的日志；产品不能依赖集中式日志服务。

**决策**：主进程写 `logs/easypush-YYYY-MM-DD.jsonl`，按天分文件，保留 14 天；内存保留最近 500 条，界面对外提供最近 400 条；诊断包附带最近 80 条。字段按键名脱敏，超长字符串截断。

**后果**：

- 日志可直接用 `jq`/文本工具分析，也可安全附加到问题报告（仍需人工检查 IP/设备名）。
- 按天轮转仅在写入时切换；跨天长期空闲后首次写入即创建新文件。
- 无日志聚合与告警；磁盘占用小但需自行清理（14 天自动）。
- 不记录媒体内容；排障能力受限于事件字段。

**备选**：系统事件日志（写入权限与格式受限）、SQLite 日志（查询强但增加依赖）。

## 变更流程

1. 新决策先在 PR/Issue 中描述背景、备选与后果，评审后追加到本文件。
2. 修改已接受决策时，新建 ADR 并在旧条目顶部标注"已被 ADR-XXX 取代"，保留原文以便追溯。
3. 安全相关决策（审批、证书、回环隔离、DLNA 暴露）必须同步更新 [安全设计](security.md) 与 [验证规范](verification.md) 的覆盖矩阵。
4. 文档中的锚点（如 `#adr-004自建本地-ca-而非公网证书`）被其他文档引用，重命名标题时必须同步修复链接。
